1. Architecture Overview

The application follows a multi-layered architecture with clear separation of concerns:

Frontend Stack

  • SvelteKit with TypeScript
  • Custom Svelte stores with reactive derived values
  • Modular component architecture with CSS modules
  • Tauri v2 for native desktop capabilities

Backend Stack

  • Rust with Tauri for IPC commands
  • SQLite database through custom ChatStore
  • Optional backend NLP service for intent classification
  • Streaming support for real-time responses

2. Core Data Model

Entity Relationships

Conversation (1:N)
├── Threads (1:N)
│   └── Messages (1:N)
└── Messages (when not threaded)

Key Types

Conversation

  • Container for threads with settings
  • Model configuration per conversation
  • Temperature and max tokens settings
  • Provider selection

Thread

  • Organizes related messages
  • Resolved/unsolved state management
  • Title and metadata
  • Atomic creation with first message

Message

  • Individual messages with roles
  • Content and timestamps
  • Status tracking (sending, sent, error)
  • Intent classification metadata

4. Message Flow Architecture

Detailed Message Flow Steps

User types in ChatInput
ChatInput validates input and triggers onsubmit
ChatArea calls chatStore.sendMessageWithLlm()
LlmHandler validates and creates optimistic message
Backend IPC command send_message()
Rust backend validates thread state
Message saved to SQLite database
Streaming request initiated
LLM events processed through event handler
Content streamed back and displayed live
Final message committed with metadata

Thread Management Flow

User sends first message in conversation
System checks for existing threads
If no threads: create_thread_with_message() atomic operation
If threads exist: select most recent thread
Thread status tracked in metadata.resolved
Backend prevents new messages to resolved threads
UI reflects resolved state with disabled input
Thread Locking Enforcement: 
if thread.metadata.resolved {
    return Err("Thread is resolved and cannot accept new messages".to_string());
}

8. Auto-Scroll System

The application implements a sophisticated auto-scroll system with multiple layers:

Scroll Controller (scrollController.ts)

  • Unified facade coordinating all scroll subsystems
  • Thread-aware: Maintains scroll state per thread
  • Smart pausing: Pauses when user scrolls up during streaming
  • Priority system: User > Programmatic > Background

Scroll Subsystems

DOM Batcher

  • Batched DOM reads/writes for performance
  • Reduces layout thrashing
  • Optimized for frequent updates

Priority Queue

  • Priority-based operation scheduling
  • Prevents scroll conflicts
  • Ensures smooth user experience

Live Animation

  • Chasing animation for smooth streaming
  • Uses requestAnimationFrame
  • Responsive to content length

State Machine

  • Explicit state management
  • Clear transition rules
  • Prevents invalid states

Auto-Scroll Behaviors

  • Auto-scrolls to bottom during streaming
  • Detects user scroll thumb dragging
  • Extended cooldown when scrolling up
  • Resumes when user scrolls back to bottom

9. LLM Streaming Architecture

Streaming Flow

User sends message → create optimistic assistant message
Initialize streaming with unique request ID
Event handler with isolated session state
Process LLM events:
  • START: Set request ID and model
  • CHUNK: Append to local content, update UI
  • COMPLETE: Finalize message with metadata
  • ERROR: Mark as failed, show error

Key Features

  • Request Isolation: Each stream has unique ID to prevent cross-contamination
  • Local Accumulation: Content built locally before UI update
  • Error Handling: Graceful fallback on stream failures
  • Cancellation: Support for canceling mid-stream
Event Handler Pattern: 
// Critical: Each stream gets its own closure
const sessionState = { requestId: null, localContent: '' };

return (event: LlmEvent) => {
    // Filter events by requestId for isolation
    if (sessionState.requestId && event.requestId !== sessionState.requestId) {
        return;
    }

    // Process events and update state
    if (isChunkEvent(event)) {
        sessionState.localContent += event.delta;
        updateUI(sessionState.localContent);
    }
};

11. Error Handling and Recovery

Error States

  • Message Send Failures: Mark as error, allow retry
  • Backend Unavailable: Show error, retry options
  • Stream Failures: Graceful fallback to static response

Recovery Mechanisms

  • Retry Logic: Users can retry failed messages
  • Optimistic Rollback: Revert state on failures
  • Error Notifications: Visual feedback for errors
Thread Resolution Error: When attempting to send to a resolved thread: 
"Thread '{thread_title}' is resolved and cannot accept new messages.
Reopen the thread to continue the conversation."
